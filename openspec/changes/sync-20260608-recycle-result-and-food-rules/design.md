## Context

目前 P2b 承載食物、體力、潔淨、公式、下週預告等多種資訊，畫面偏工程結果單，缺少 Buddy 世界的成就感。2026-06-08 會議將回收結果重新拆成兩層：主畫面先讓使用者感受到「這次帶回多少」，細節才說明數據怎麼來。

舊規格同時存在兩個需要收斂的矛盾：一是食物效果仍寫成普通 +10 / 稀有 +15，二是回收直接加體力與食物餵食加體力重疊。新決策改為回收先給食物與潔淨，體力主要由後續餵食食物取得，且同食物餵食效果為 +1~5 random。

## Goals / Non-Goals

**Goals:**
- 讓 PM 決策稿明確列出「牽動畫面」與「調整部分」。
- 讓 P2b 以回收總量為主視覺，細節資訊降層。
- 明確切開收瓶機與電池機，不讓兩種數據同時出現在同一結果狀態。
- 讓食物發放、潔淨結算與食物餵食效果都有清楚的資料責任。
- 補上 P2b 返回 P1 的潔淨增量動畫。

**Non-Goals:**
- 不在本 change 決定 P1「食物欄」最終新名稱，只標記為 PM 待命名。
- 不重做 P1 首頁完整 IA。
- 不定義 random 演算法權重，只要求後端回傳本次結果。

## Decisions

1. **P2b 主畫面採「大字總量 + 小字細節」**
   - 主視覺顯示本次回收總量，例如「帶回 6 件」。
   - 收瓶機細節顯示瓶/杯/退件等；電池機細節顯示電池件數/規格。
   - 公式與完整細節放在小字說明或摺疊區，避免干擾成就感。

2. **回收結果 payload 以 machine_type 分流**
   - `machine_type = bottle` 或 `machine_type = battery` 二擇一。
   - 前端不得在同一 P2b 狀態同時顯示投瓶數與投電池數。
   - 若 API 回傳混合資料，前端應顯示資料異常狀態並要求重新整理/重掃，不自行合併。

3. **回收先給食物與潔淨，餵食才加體力**
   - 回收完成當下結算潔淨，P2b 顯示本次 `clean_delta`。
   - 食物受後台上限限制，P2b 顯示本次實際發放數與上限狀態。
   - 食物餵食後由後端回傳本次 `hp_delta`，範圍為 +1~5。

4. **P2b → P1 潔淨動畫是獨立回饋**
   - 返回 P1 後，在 Buddy 或狀態條附近播放「+? 潔淨」動畫。
   - 這個動畫與食物欄 Badge pop 可同時發生，但層級上潔淨動畫應靠近 Buddy/狀態條，食物動畫靠近食物格。

## Risks / Trade-offs

- [Risk] 舊文件仍有 HP / 固定 +10/+15 殘留，工程可能照舊實作 → Mitigation: 同步 `GAME_MECHANICS.md`, `USER_FLOW.md`, `UI_SPEC.md`, `FAQ.md`，並在 OpenSpec 標註修改。
- [Risk] random 效果若由前端抽會產生作弊與一致性問題 → Mitigation: 後端決定本次結果，前端只顯示回傳值。
- [Risk] P1「食物欄」名稱未定會阻塞 UI 文案 → Mitigation: 文件保留內部代稱，PM 補命名前不得把待定名稱當最終用戶文案。
