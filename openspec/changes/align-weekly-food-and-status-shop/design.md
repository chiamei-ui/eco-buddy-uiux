## Context

hi-fi 的 food state 仍把 W1–W4 視為四個獨立格，P2b、P4、P5 分別增量，且 P4 付款模型只能選點數或現金。此 change 將原型收斂為一個可追蹤的當週食物實體與一筆合併付款資料；正式版資料仍由後端／商店設定提供。

## Goals / Non-Goals

**Goals:**

- 讓 P1、P2b、P4、P5 使用同一個當週食物存量與週配額。
- 呈現餐袋總量 12、週配額 5、週三重置、月底清空與只看不拿的預告。
- 讓已定案的食物、玩具與禮包付款規則在 hi-fi 一致。
- 顯示狀態禮包框架，且不越過未決的數值／可售清單邊界。

**Non-Goals:**

- 不決定一般回收是否直接增加體力，或超額投遞是否增加潔淨。
- 不決定裝扮付款方式、可販售狀態清單、禮包 2 價格與任何禮包數值效果。
- 不實作真實 API、平台 IAP、後台排程、月結排程或 Rive FX4 的刪除／轉用。
- 不同步修改既有 `docs/`；新規則先由本 change 的 spec 與 hi-fi 實作承接。

## Decisions

### 1. 單一 food state 作為原型真相來源

`food` 改為一筆當週食物資料，包含 `weeklyCount`、`bagCount`、`weeklyLimit: 5`、`bagLimit: 12`、`currentFood` 與 `nextFood`。回收、商店與今日陪伴都透過同一增量 helper 嘗試加一；helper 同時檢查兩個上限，回傳是否已滿。這比保留多格再同步計數更少分支，也不會讓商店繞過週配額。

替代方案是保留四格後以 source 欄位分組計數；不採用，因為四週格本身已被退役且容易重現多來源不同步。

### 2. 超額與未決數值隔離

當 `weeklyCount === 5` 時，回收結果不給食物、不加超額體力。`cleanGain` 維持原型既有資料值，但以開發註解標明等待待決議-3；一般回收的體力來源不在本 change 改寫。這可先落實已拍板的超額紅線，避免假裝解完未決來源模型。

### 3. 合併付款資料模型

玩具與禮包使用 `pointsCost` 與 `iapPrice` 同時存在的商品資料；確認頁同時檢查點數與 IAP 可售狀態，成功後一次寫入點數訂單與 IAP 訂單展示資料。食物只有 `pointsCost`，裝扮維持不變直到待決議-4。

替代方案是將一個商品拆成兩張卡；不採用，因為會讓使用者誤以為可只付其中一種貨幣。

### 4. 狀態禮包只建立未越界骨架

禮包 1 顯示「#1–27 候選範圍、可重複購買、一次解鎖一個」；禮包 2 在價格與可售名單未定前不開啟購買。兩者都不得改寫 hp／clean／mood。實際抽取、可售狀態名單、數值同步與收藏門檻由後端／PM 決策後再接入。

### 5. 月結只清餐袋，不清玩具

新增專用的餐袋清空 action；不復用目前錯誤命名且會清除玩具的 `CLEAR_BAG` action。原型控制項可模擬週三重置與月底清空，方便驗收狀態。

## Risks / Trade-offs

- [Risk] 原型使用固定當週食物示例，可能被誤認為排程資料 → Mitigation：資料結構保留 `currentFood`／`nextFood` 欄位與開發註解，正式版由排程 API 供應。
- [Risk] 合併付款尚無真實 SDK → Mitigation：hi-fi 只模擬確認狀態，不宣稱可完成平台交易。
- [Risk] 舊 OpenSpec 與文件仍主張稀有食物／純現金 → Mitigation：本 change 以 delta 明確移除，後續 PM 正式落檔時再同步文件與動畫交接。
- [Risk] 待決議被 UI 文字暗示為定案 → Mitigation：未定價格與未定效果不顯示成可購買或可生效的結果。

## Migration Plan

1. 先新增本 change 與 strict validation。
2. 將 hi-fi food state 與 reducers 收斂，再更新 P1、P2b、P4、P5 與購買確認頁。
3. 以原型控制項驗證三來源共享配額、達 5 禁購、月底清空與付款不足。
4. 待 PM 補齊六項決議後，更新正式 docs、API contract、商品 SKU 與動畫交接。
