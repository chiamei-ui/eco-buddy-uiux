## 一、專案概述

本專案透過 Rive 技術開發一套具備高度互動性與資料驅動（Data-driven）特性的電子寵物動態系統。核心角色採月度輪替制，每月發放一隻限定月度角色，品牌定位為有趣、永續且全齡友善。

寵物須根據後端即時傳入的數值，流暢地在多種型態組合之間切換。完整型態規格見 [CHARACTER_TYPES.md](CHARACTER_TYPES.md)，動作事件見本文件 §七，音效規格見 §八。

**設計核心原則**：基於 O2O 循環經濟的「環保行為具象化」養成體驗，透過遊戲化機制提升用戶回收黏著度。各月度角色須具備清晰的臉部識別元素，所有表情變化透過嘴巴、臉頰、身體語言呈現。風格參考：Apple / MUJI 極簡設計語彙。

## 二、月度角色制

### 核心邏輯

系統每月 1 日自動發放當月新角色，用戶於月內進行養成互動。月末結算後，角色依最終三大屬性數值組合決定收藏等級並歸檔，同時推播下月角色預告。

- 每月角色外觀設計不同，但狀態機命名規範、插槽架構與事件埋點維持完全一致
- 角色發放初始數值：`hp_level 50 / clean_level 50 / mood_level 50`（即預設型態 #14「環保初心」）

### 單一骨架架構原則

每月新角色採用相同骨架架構，僅替換外觀 Skin。Phase 1 建立的骨架必須具備足夠彈性，以支援後續每月不同外觀的 Skin 替換。

**Phase 1 重點**：建立可參數驅動、可月度 Skin 替換的骨架地基。骨架品質直接決定後續所有月度角色的製作效率。

Phase 0B（對齊期）須由外包以書面提出骨架具體拆分方案、臉部識別元素縮放規則及命名對齊，同時確認 Rive Editor 版本號與對應 Runtime 版本號。Phase 0B-2 書面確認要求（RFP v1.2 新增 C-0B2-1–3；v1.4 擴大新增 C-0B2-4–5），須全部取得甲方書面確認後方可進入 Phase 2：（C-0B2-1）3.6 元素圖層拆分計畫；（C-0B2-2）State Machine 名稱 `BuddyMachine` 與 input 命名確認；（C-0B2-3）所有 `ev_*` trigger 逐一觸發命名對齊測試；（C-0B2-4）代表性架構可行性 PoC（可用簡易佔位素材，驗證 Idle 疊加、has_* 骨架附著、#27→#36 銜接、#33 轉場邏輯、核心動作事件返回機制）；（C-0B2-5）Pivot／Bounds／Draw Order 基準表確認（須經甲方書面確認後方可作為 C-P2-6 及月度驗收依據）。

## 三、核心技術架構

### 3.1 開發原則

- 採「單一骨架（Single Skeleton）」搭配「狀態機（State Machine）」與「插槽系統（Slot System）」
- 嚴禁為各別型態建立獨立檔案，所有型態切換必須在單一 `.rev` 原生檔案中實作
- 優先使用變換約束（Transform Constraints）減少手動關鍵影格，提升可維護性
- 所有變數與事件命名必須嚴格遵守命名手冊 v1.2（大小寫與底線須完全一致）
- 開發啟動前須書面確認 Rive Editor 版本號及對應 Runtime 版本號

### 3.2 三大核心屬性參數

後端以整數（0–100）傳入三個參數，分三個階層觸發視覺變化。後端若傳入非整數值，Rive 狀態機須以 `floor()` 無條件捨去後再判斷。

**階層定義**：低（Low）：0–30　｜　中（Mid）：31–65　｜　高（High）：66–100

#### hp_level — 體型縮放

| 參數名稱 | 類型 | 數值範圍 |
|---------|------|---------|
| `hp_level` | Number | 0–100 |

| 階層 | 數值 | 視覺效果 |
|------|------|---------|
| 低 | 0–30 | 視覺呈現偏低，以扁薄、姿態下沉、低能量輪廓傳達虛弱體態；臉部核心識別元素比例須保持固定 |
| 中 | 31–65 | 標準比例基準，線條俐落；臉部核心識別元素比例須保持固定 |
| 高 | 66–100 | 視覺量感約為 mid 基準之 105–115%，以姿態挺立、輪廓飽滿傳達健康活力；臉部核心識別元素比例須保持固定 |

各階層內固定縮放，階層間以 State Machine 過渡動畫切換，**嚴禁**以 1D Blend Axis 線性映射實作。

#### clean_level — 潔淨外觀

| 參數名稱 | 類型 | 數值範圍 |
|---------|------|---------|
| `clean_level` | Number | 0–100 |

| 階層 | 數值 | 視覺效果 |
|------|------|---------|
| 低 | 0–30 | 滿布髒污粒子，色彩飽和度降低 40%（低階內部線性過渡：level=0 時 −40%，level=30 時 0%；此為本專案唯一允許的 1D 連續映射例外） |
| 中 | 31–65 | 霧面乾淨材質，色彩還原 100% |
| 高 | 66–100 | 材質趨於輕盈透亮，晶透折射質感；含發光光暈及微粒子漂浮 |

#### mood_level — 心情表情

| 參數名稱 | 類型 | 數值範圍 |
|---------|------|---------|
| `mood_level` | Number | 0–100 |

| 階層 | 數值 | 視覺效果 |
|------|------|---------|
| 低 | 0–30 | 眉毛下垂、嘴角向下、姿態下沉 |
| 中 | 31–65 | 中性表情、規律眨眼、微幅律動 |
| 高 | 66–100 | 瞳孔放大、嘴角上揚、愛心粒子 |

依 mood_level 三段階層以 Rive State Machine 離散切換，**嚴禁**以 1D Blend Axis 線性映射實作。

> 三個參數各分三階層，3×3×3 共構成 27 種基礎型態。後端串接與 Rive Runtime 呼叫由甲方工程師自行實作。

### 3.3 預設型態規格（#14「環保初心」）

| 參數 | 預設值 | 視覺說明 |
|------|-------|---------|
| `hp_level` | 50 | 標準體型 100%，線條俐落 |
| `clean_level` | 50 | 霧面乾淨材質，高質感 |
| `mood_level` | 50 | 中性表情，規律眨眼，溫和微笑 |
| 整體風格 | — | 乾淨霧面高質感；Apple / MUJI 極簡設計語彙；平靜呼吸，溫和微笑 |

Phase 1 驗收時須能正確呈現此預設型態，並提供 `.riv` 發布檔供工程師進行 Runtime 初步串接測試。

### 3.4 Idle 待機循環規格

三種 Idle 循環依 mood_level 階層自動切換。所有 Idle 須為無縫循環（Seamless Loop），首尾影格銜接自然，不得有跳動或停頓感。

| Idle 類型 | 循環時長 | 動作描述 |
|----------|---------|---------|
| 低 mood Idle | 5 秒 | 偶爾嘆氣 ＋ 耳朵下垂；整體姿態低沉，動作幅度小 |
| 中 mood Idle | 4 秒 | 規律眨眼 ＋ 偶爾回頭張望；自然待機狀態 |
| 高 mood Idle | 3 秒 | 左右輕微搖擺 ＋ 哼歌嘴型；活潑有節奏感 |

### 3.5 臉部識別元素固定規則

角色臉部核心識別元素（眼睛、腮紅、嘴巴）在 `hp_level` 極值縮放時，比例須保持固定，**不得**跟隨骨架等比縮放而變形。縮放規則須於 Phase 0B 骨架拆分方案中由外包提出，並經甲方書面確認。

### 3.6 狀態專屬視覺元素規則（RFP v1.2 新增）

每一個基礎型態（#01–#27，#14 除外）各有一組「狀態專屬視覺元素」，作為該型態的視覺身份識別，共 **26 個狀態項目**。

**基本規則：**
- 由 Rive State Machine 依 hp_level／clean_level／mood_level 解析後的當前基礎狀態自動控制顯示／隱藏
- **不使用 `has_*` Boolean，後端不傳值**
- 元素附著於骨架節點，隨骨架移動，**不得具有獨立循環動畫、粒子發射或專屬 timeline**
- 命名格式：`state_<NN>_<type>_<descriptor>`；type 限 `prop`（道具）、`decor`（裝飾飾品）、`decal`（貼花）、`mark`（符號標記）
- 完整 26 個狀態規格見 [NAMING.md §四](NAMING.md) 及命名手冊 v1.2「State-Specific Visual Elements」分頁

**跨月度沿用規則：**
- （b-1）預設沿用首版美術造型，月度設計師調整位置與縮放比例
- （b-2）若月度角色風格不適合直接沿用，得於月度合約附件另約局部重繪，但不得新增後端 input、不得變更 State Machine、不得改變 26 個狀態項目數量

**特殊型態覆蓋優先序（決定 3.6 元素是否顯示）：**

| 優先序 | 類型 | 觸發條件 | 3.6 元素 |
|---|---|---|---|
| g-1（最高）| 取代型 | `has_dark=true` | 全部隱藏 |
| g-2 | 全身覆蓋型 | `has_bottle / has_armor / has_golden=true` | 全部隱藏 |
| g-3 | 頭頂飾品型 | `has_laurel / has_disco / has_halo / has_cycle_crown=true` | 頭頂位置隱藏，其他並存 |
| g-4（最低）| 疊加型 | `has_overfed / has_frenzy=true` | 全部並存 |

**Phase 0B-2 須提交（C-0B2-1）：** 26 個狀態逐一清單、主命名、預計子圖層、骨架附著位置、與 S1–S10 及 FX 可能衝突說明，甲方書面確認後方可進入 Phase 2。

### 3.7 月度替換架構鎖定規則（RFP v1.2 新增）

月度替換**只能更換 Skin（視覺素材層）**，不得變更控制層。以下項目首版建立後鎖定：

| 鎖定項目 | 說明 |
|---|---|
| State Machine 名稱 | `BuddyMachine`，固定不得改名 |
| Core Input 命名 | `hp_level` / `clean_level` / `mood_level`，範圍 0–100，不得新增或改名 |
| 事件命名 | 所有 `ev_*` trigger 命名鎖定，不得新增或改名 |
| Rive 內部型態對應 | `morph_01`–`morph_27` 為 Rive 內部識別名，**非後端 input**，後端不傳送此類變數 |
| Pivot / Bounds / Draw Order | 首版 Phase 0B-2 確立基準，月度可在安全範圍內微調，不得造成位移錯位或遮擋錯亂 |

**月度合約驗收繼受（RFP v1.4 §3.7(d)，由 3 項擴大為 8 項）：** C-0B2-2（State Machine 名稱 `BuddyMachine` 與必要 input 命名鎖定）、C-0B2-3（事件 Trigger 命名與存在性）、C-P2-2（骨架附著律動）、C-P2-3（狀態切換轉場）、C-P2-6（pivot／bounds／draw order 安全範圍）、C-1（S1–S10 插槽架構）、C-P3-4（#33 取代型視覺邏輯）、E-4（音效素材沿用，含檔名與事件對應）需在每次月度替換時重新檢核，不得取消。上述項目僅驗證架構與命名一致性；視覺內容得依當月主題重繪。

## 四、效能門檻與壓力測試規格

### Phase 1 基礎要求

| 項目 | 要求 |
|------|------|
| Rive Editor 版本 | Phase 0B 對齊期間書面確認版本號；版本升級須事先獲甲方書面確認 |
| 檔案格式 | 100% 向量路徑（Vector Paths），嚴禁使用點陣圖 |
| 最終發布檔 `.riv` | < 120KB（Phase 1 試作即須符合） |
| 快速變量測試 | 1 秒內 hp_level / clean_level / mood_level 各自重複切換 0↔100，不得產生破面或異常形變 |
| 佈局設定 | Rive Layout 響應式佈局；暫定展示框比例 3:4（寬:高）；角色座標原點固定底部中心；參考裝置 iPhone 15（390pt）及 Android（360pt） |

### Phase 2–4 完整壓力測試規格（RFP §8.2；F 組正式編號以附件「開發驗收檢核表」為準，本表僅列測試規格不重編號）

| 測試類別 | 測試方法與通過標準 |
|---------|-----------------|
| 檔案體積 | 最終發布檔（.riv）須控制在 120KB 以內 |
| 記憶體監控 | 記憶體增加量不得超過 15MB。基準點：Rive 場景載入完成、進入 Idle 狀態且尚未發生任何互動之記憶體用量；測試裝置：iOS 為 iPhone 15，Android 為 **Android 12 以上、RAM ≥ 6GB、中高階等級 SoC**（如 Snapdragon 7 系列以上）；量測工具：iOS 用 Xcode Instruments（Allocations）、Android 用 Android Studio Profiler（Memory）；量測區間：F-4 長時間運作測試（Idle 60 分鐘）全程（RFP v1.4 新增具體裝置門檻與量測工具，前版僅泛稱「360pt 等級裝置」） |
| 快速變量測試 | 1 秒內各自獨立重複切換 hp_level / clean_level / mood_level 至極值（0 與 100 交替），不得產生破面或異常形變 |
| 高頻觸發測試 | 主要動作事件（§6.2 之 10 大動作事件）各於 1 分鐘內觸發 20 次，須同時通過雙判定：**3-A CPU 播放後回復**——先量測 Idle 穩態基準（靜置 ≥2 分鐘，取 60 秒平均，每輪開始前重測），該動作最後一次觸發播放完畢後等待 1 秒，觀測 process CPU 之 1 秒移動平均，若連續 >3 秒仍高於 max（基準 ×2.5，基準 ＋10 個百分點）即判定該子項不通過；瞬間 CPU 上升不算。**3-B 畫面流暢度**（同一測試中量測）——需同時符合：P95 幀耗時 ≤20ms（60Hz 基準）、單幀 >33ms 每測試分鐘 ≤3 次、無連續 3 秒平均 FPS <55，任一項不符即該輪 3-B 不通過。3-A／3-B 皆以與 Release 候選版同原始碼／功能／資產之 Flutter Profile build 量測；Release 版僅加測一輪確認無閃退與功能異常，不重跑 3-A／3-B。首輪任一子判定未過，得於同裝置／版本／更新率／測試條件下加測兩輪，三輪中同一子判定累計 ≥2 輪未過才判定 F-3 不通過；任一版本任一輪發生閃退則立即不通過，不適用複測。測試裝置規格與量測工具與 F-1 一致，實際機型與螢幕更新率（鎖定 60Hz）由甲方於驗收前 14 日書面指定。（**RFP v1.4 更新 2026-07-17**：取代前版「CPU 持續超過 Idle 基準 1.5 倍」單一判定，改為 3-A/3-B 雙判定＋複測歸因機制；F-1／F-3 未過可依驗收注意事項第 4 項於最小重現環境複測釐清責任歸屬） |
| 長時間運作 | 連續播放 Idle 動畫 60 分鐘，不得有記憶體洩漏或閃退現象 |
| 佈局響應式 | 於各螢幕比例（19.5:9 / 19.6:9 / 20:9）測試，確認角色座標原點固定於底部中心，無裁切異常 |

## 五、Phase 1 驗收項目

| 編號 | 驗收項目 | 等級 |

| A-3 | 交付 .riv 發布檔（含 #14「環保初心」預設型態之初版）供工程師 Runtime 初步串接測試；須符合 < 120KB | 必要 |
