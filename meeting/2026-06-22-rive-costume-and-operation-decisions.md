# 2026-06-22｜Rive 裝扮製作與營運設定待決策

**會議目的**：確認封測前裝扮要做到「看得到」還是「真的可穿戴」，並釐清禮包可設定欄位、食物配額與跨月保存規則。

**建議與會者**：PM、UI/UX、窗口設計師、前端、後端；裝扮範圍確認後由窗口設計師向 Rive 外包詢價。

**文件性質**：會議討論稿。未經會議定案，不取代 `docs/decisions/CURRENT.md`。

---

## 一、先講結論

### 1. 第一隻角色的裝扮製作順序

如果封測要求裝扮「實際套在海龜 Rive 角色上」，流程確實是：

```text
海龜主要骨架與變形規則驗收
→ 確認裝扮插槽位置、縮放與遮擋規則
→ UI/角色設計師依核准骨架設計裝扮
→ Rive 外包將裝扮綁入插槽
→ 測試體力 60% / 100% / 140% 與各狀態
→ 前端 Runtime 串接與真機驗收
```

裝扮概念可以提早設計，但最終尺寸、定位、遮擋與變形仍須等海龜骨架／插槽規則穩定後校正。否則很容易發生角色變胖、變瘦或動作時穿模，需要重新繪製與重新綁定。

### 2. 後續月度角色

後續角色可將「角色三視圖＋裝扮三視圖」一起交付，但前提是第一隻海龜已建立可重複使用的：

- 插槽命名與錨點位置
- 配件圖層順序與遮擋規則
- 不同體型的縮放／變形規則
- Runtime mapping 與驗收範本

即使商品 ID 與帳號持有權共用，每個角色仍需有自己的裝扮適配素材與 Rive 綁定驗收。不能假設同一張王冠或護甲圖直接套到所有角色都會正確。

### 3. 封測建議

**建議採「顯示裝扮商品概念卡，但不提供實際試穿／穿戴」。**

這符合既有 PM 決策「Phase 1 顯示 2–3 款 hero 卡、CTA disabled」，也符合 OpenSpec「Phase 1 可顯示靜態預覽圖，但不提供試穿動畫」。

封測若要求真正可穿戴，等同把原本列在正式合約 Phase 3 的 S1–S10 插槽工作提前，會新增外包變更、驗收與前端串接風險。

## 二、目前 repo 已確認的規格事實

### Rive 合約範圍

- Phase 1 目前範圍是單一骨架、三參數、三種 Idle、臉部比例與命名驗收。
- S1–S10 配件插槽在正式合約 Phase 3，不是 Phase 1 試作交付。
- 配件驗收要求配件跟隨骨架變形，且不得破面。
- 月度角色雖沿用相同狀態機與插槽規範，仍需交付一套新的角色 `.rev` 外觀。
- Repo 沒有外包日費率、單款裝扮報價或修改次數價格，因此無法直接推算確切 NT$。

### Phase 1 裝扮 UI

- PM 決策 #28：Phase 1 顯示 2–3 款 hero 裝扮商品，CTA 為「即將開放」。
- 商店 OpenSpec：Phase 1 商品卡可顯示靜態預覽，不開啟試穿動畫。
- P1 換衣間流程：Phase 1 只顯示「即將推出」，Phase 2 才顯示可穿上／脫下的裝扮。

因此「Phase 1 顯示裝扮」目前合理解讀應是：

> 商店顯示未開放的商品概念卡，不代表封測必須完成可穿戴 Rive 資產。

## 三、第一隻海龜的建議製作流程

| 階段 | 主要產出 | 負責角色 | 可否與主角色並行 |
|---|---|---|---|
| 1. 主骨架驗收 | `.rev`、三段體型、Idle、圖層結構 | Rive 外包＋窗口＋前端 | 基礎工作 |
| 2. 插槽規則確認 | 錨點、圖層順序、縮放、遮擋、Boolean mapping | Rive 外包＋窗口＋前端 | 須以穩定骨架為準 |
| 3. 裝扮視覺設計 | 裝扮三視圖、材質、配色、遮擋說明 | UI/角色設計師 | 概念可並行，定稿不可 |
| 4. Rive 適配 | 向量圖層匯入、綁定、變形／遮擋設定 | Rive 外包 | 依賴 1–3 |
| 5. Rive 驗收 | 低／中／高體型、Idle、快速變量、破面測試 | 窗口＋前端 | 依賴 4 |
| 6. App 串接 | 商品 ID、持有權、插槽 Boolean、試穿／換裝 | 前端＋後端 | 可先建資料結構，最終驗收依賴 5 |

### 裝扮交付稿不能只有三視圖

建議每件裝扮另外附：

- 對應插槽：S1–S6
- 正面基準位置與角色錨點
- 前景／後景圖層拆分
- 哪些部位會被身體、帽子或四肢遮住
- 體型 60%／100%／140% 的縮放或變形示意
- 是否允許與其他裝扮同時顯示
- 動態效果、粒子與循環時間

## 四、時程與外包成本推斷

以下為依 repo 驗收複雜度做的**規劃估算，不是外包報價**。正式金額須由窗口設計師提供 `.rev` 與裝扮需求後，向 Anastasiia 取得書面報價。

### 外包工時推斷

| 工作 | 規劃估算 |
|---|---:|
| 首次建立／確認裝扮插槽、錨點與圖層規則 | 2–4 外包人日 |
| 光環等不貼身簡單配件 | 0.5–1.5 人日／款 |
| 王冠、帽子等需跟隨頭部動作配件 | 1–3 人日／款 |
| 護甲、身體覆蓋等需隨體型變形配件 | 3–5 人日／款 |
| 2–3 款整體驗收、修改與 `.riv` 重出 | 2–4 人日 |

若 Phase 1 提前製作「彩虹光暈＋循環王冠」兩款，保守抓：

- **外包投入：約 5–10 人日**
- **排程：約 1–2.5 週**
- 若再加入護甲或身體覆蓋款：建議再加 **3–5 人日**
- 若骨架仍在修正，應另保留 **20–30% 重工緩衝**

### 費用計算方式

Repo 沒有日費率，會議中不應承諾固定金額。可用下式先做預算：

```text
追加外包費
= 外包日費率 × 5–10 人日
+ 合約變更／急件費
+ 超出約定修改次數的重工費
```

### 為什麼第一隻角色成本最高

- 首次建立配件插槽與驗收規則，後續角色才能沿用。
- 海龜骨架若尚未完全驗收，裝扮可能跟著返工。
- 裝扮需測試體型 60%／100%／140%，不是只確認一張靜態圖。
- Phase 1 `.riv` 有 120KB 體積門檻，增加向量與粒子可能影響效能與檔案大小。
- 現有 Phase 1 合約未含 S1–S10，提前製作可能需補充報價或合約變更。

## 五、封測方案比較

| 方案 | 封測呈現 | 新增外包 | 時程風險 | 建議 |
|---|---|---:|---:|---|
| A. 靜態商品概念卡 | 顯示 2–3 款 hero 卡、即將開放；不試穿 | 無或僅輸出靜態圖 | 低 | **建議** |
| B. 只做 1 款簡單可穿戴 | 優先彩虹光暈；可展示 Runtime 插槽能力 | 約 3–7 人日 | 中 | 若一定要驗證穿戴 |
| C. 2–3 款完整可穿戴 | 光暈、王冠、護甲皆可試穿 | 約 8–15 人日 | 高 | 不建議塞進封測 |

### 建議決策

1. Phase 1 保留 2–3 款靜態 hero 卡，CTA disabled。
2. 卡片文案避免暗示封測期間可穿戴，統一寫「即將開放」。
3. 正式合約先完成插槽地基，再製作實際商品。
4. 若商業端堅持封測展示穿戴，範圍限縮為一款不貼身配件「彩虹光暈」，不要同時做王冠與護甲。

## 六、裝扮與角色共用規則待決策

### 建議資料規則

- 商品 ID、購買 entitlement、名稱與售價：可跨角色共用。
- Rive 視覺素材、錨點與遮擋設定：每個角色各自適配。
- 商品需有 `supported_character_ids` 或相容性資料。
- 尚未完成適配的角色，不顯示試穿與穿戴 CTA。

- [ ] 第一款可穿戴裝扮是否限定彩虹光暈？

## 七、禮包可供行銷設定的變因

前端可以先定義資料欄位，但正式內容建議由後台／CMS 或 API 控制。

### 建議可設定欄位

- 商品名稱、圖片、短文案、詳情文案

- 顯示排序、活動標籤
- 內容物 ID、數量、有效期
- 是否占用每週食物配額
- 每帳號購買次數
- 適用客群或活動條件
- 金流 SKU、追蹤活動 ID

### 會議需確認

- [ ] 哪些欄位行銷可自行修改？
- [ ] 哪些欄位涉及經濟平衡，必須經 PM／後端審核？

- [ ] 商品內容變更後，既有訂單顯示「購買當下快照」還是最新內容？

## 八、每週食物配額與每月角色切換

### 建議規則

- 每週重置的是「可取得配額」，不是既有庫存。
- 月初換角色時，已取得且未使用的食物不消失。
- 食物綁帳號與 `food_id`，不綁當月角色。
- 若特定活動食物必須過期，取得前就要顯示明確期限，並保留合理使用寬限期。

### 不建議月底全部清空

月底清空會造成：

- 月底才取得食物的用戶可使用時間較短。
- 用戶可能為了省食物而不敢餵 Buddy。
- 商店購買或禮包取得的食物若被清除，容易產生退款與公平性爭議。
- 「每週配額」與「每月清空」雙重限制，會讓規則過度複雜。

### 會議需確認

- [ ] 一般食物是否永久保存至用完？
- [ ] 活動／月份限定食物是否有期限？
- [ ] 月底衝刺禮包食物能否帶到下個月？
- [ ] 食物格上限 12 與每週配額 5 的關係是否維持不變？
- [ ] 月初新角色是否接受上月食物？

## 九、會議建議決議順序

1. 先決定 Phase 1 裝扮只顯示靜態卡，或需要真實穿戴。
2. 若需穿戴，決定只做一款或 2–3 款，並由窗口向外包詢價。
3. 決定裝扮 entitlement 是否跨角色共用。
4. 決定禮包後台可設定欄位與審核權限。
5. 決定一般食物與限定食物的跨月保存規則。
